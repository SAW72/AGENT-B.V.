# Spencer setup for the Agent-B.V. points Worker

Agents ran none of these steps. No agent logged in, deployed, or set a secret. No Cloudflare resources were created from this branch.

Do this on your Mac, from a checkout of this branch. The working directory is `services/points-indexer/cloudflare`.

1. Use the Cloudflare account that owns `agent-bv.pages.dev`, or create a free account and keep this Worker on that same account.
2. Run `npx wrangler login`.
3. Run `node check-chain.mjs`. It reads `CHAIN_ID` from `wrangler.toml` and exits if the value is not `84532`. The Worker reads the same variable on every alarm and refuses any other chain. Do not continue if this step fails.
4. Run `npx wrangler deploy`. The `v1` migration creates the Worker and the SQLite Durable Object class `PointsObject`. No D1 database is used. The file declares three rate limit bindings. Each `namespace_id` is an integer you choose so the counters stay unique in this Cloudflare account. Deploy does not create that integer. It is not an account id and it is not a secret. Two bindings that reuse one id share counters. Do not use `1001`. That number is the example in Cloudflare's docs, so another Worker on the account would share the counter.
   - `POINTS_RATE_LIMITER`, namespace `84532001`: 60 requests per 60 seconds, one bucket per client address, for an enabled `/v1/points/*` request that is not `OPTIONS`.
   - `POINTS_HEALTH_LIMITER`, namespace `84532002`: 12 requests per 60 seconds, one bucket per client address, for an enabled `/health`.
   - `POINTS_GLOBAL_LIMITER`, namespace `84532003`: 50 Durable Object wakes per 60 seconds for the whole location, on one shared key. These bindings count separately in each Cloudflare location. This cap is charged only when the request is about to call the object. An enabled `/health` charges it on a cache miss.
   `OPTIONS`, a disabled route, and an unknown path are not counted. A request with no `CF-Connecting-IP` is rejected with 400 `client_address_required` and is not placed in a shared bucket.
   On an enabled `/health` or `/v1/points` request that has a client address, the per-address limiter runs first. A repeated query parameter then returns 400 `duplicate_query`. That 400 still uses one per-address slot. It does not use the global cap, and it does not wake the object. The same 400 is returned for a repeated parameter on `OPTIONS`, a disabled route, and an unknown path, without using a limiter slot.
5. Set the RPC endpoint only with `npx wrangler secret put BASE_SEPOLIA_RPC_URL`, then paste the value at the prompt. Use your keyed endpoint or the public Base Sepolia JSON-RPC endpoint. A plain var is wiped by the next `wrangler deploy`. A secret is kept. Do not put the URL in `wrangler.toml`, `.dev.vars`, or the repo. The first alarms report `config_error` and reschedule until this secret exists.
6. Leave `POINTS_ENABLED` unset until the Verifier gives GO. Only the exact string `true` turns the indexer on. `TRUE`, `1`, `yes`, `on`, and a padded value stay off. While it is off, `/health` returns 503 `{ "status": "disabled" }` and does not wake the Durable Object. `OPTIONS` is answered in the front Worker and does not wake it either. `/v1/points/*` returns 503 `points_disabled`. When it is on, `/health` is limited per address, then stored in the Cache API for 15 seconds, so a poll does not wake the object on every call. A cache miss counts against the global cap and then reads the object, because that is where behind/ok is stored. `/v1/points/*` counts against the per-address limit and the global cap before the object is called.
7. Free plan budgets, for one location:
   - Durable Object requests: 100,000 per day, and alarms count. A caught-up alarm every 15 seconds is 86,400 / 15 = 5,760 requests a day. The global HTTP cap is 50 per minute, which is 72,000 a day. The sum is 77,760, leaving 22,240 for extra catch-up alarms on the 1 second cadence. A full day of 1 second alarms is about 86,400 by itself and does not fit beside a full HTTP cap, so a long catch-up has to stay short. The cap is per location. Several saturated locations can add past 100,000. This is the control available on the Free plan.
   - Rows written: 100,000 per day. QA measured about 63,000 rows a day at steady state, about 10 meta rows and one alarm schedule on each 15 second pass. Reads do not write a hit table. The front Worker limits in front of the object. A full day in the 1 second catch-up loop can pass 100,000 row writes. Watch the row counter if the cursor stays behind.
   - If stored logs pass 500, a rebuild stops, the rows already stored stay, and `/health` reports `rebuild_capped`. That bounds CPU when someone emits a flood of cheap logs.
   - The `nonces` and `origins` tables are intentionally unwritten, so scores stay at 0 until screening fails closed.
8. Later, when the lookup UI exists, put the Worker URL in `apps/wallet-ux` and rebuild that app. Do that only after the Verifier GO.
9. Confirm the Render dashboard has no `points-indexer` service. `services/points-indexer/render.yaml` says nothing there is deployed. There is nothing to retire.

Workers Logs are on with `head_sampling_rate` 1, so our error and lag lines are kept. `observability.logs.invocation_logs` is false, so Cloudflare's per-request invocation log is not stored. Traces stay off (`enabled` false and sampling 0) on their own. `.dev.vars` and `.wrangler/` are gitignored.

# Spencer setup for the Agent-B.V. points Worker

Agents ran none of these steps. No agent logged in, deployed, or set a secret. No Cloudflare resources were created from this branch.

Do this on your Mac, from a checkout of this branch. The working directory is `services/points-indexer/cloudflare`.

1. Use the Cloudflare account that owns `agent-bv.pages.dev`, or create a free account and keep this Worker on that same account.
2. Run `npx wrangler login`.
3. Run `node check-chain.mjs`. It reads `CHAIN_ID` from `wrangler.toml` and exits if the value is not `84532`. The Worker reads the same variable on every alarm and refuses any other chain. Do not continue if this step fails.
4. Run `npx wrangler deploy`. The `v1` migration creates the Worker and the SQLite Durable Object class `PointsObject`. No D1 database is used. The file declares three rate limit bindings. Each `namespace_id` is an integer you choose so the counters stay unique in this Cloudflare account. Deploy does not create that integer. It is not an account id and it is not a secret. Two bindings that reuse one id share counters. Do not use `1001`. That number is the example in Cloudflare's docs, so another Worker on the account would share the counter.
   - `POINTS_RATE_LIMITER`, namespace `84532001`: 20 requests per 60 seconds, one bucket per client address, for an enabled `/v1/points/*` request that is not `OPTIONS`. One client at this limit cannot fill the location's 50 per minute global wake cap.
   - `POINTS_HEALTH_LIMITER`, namespace `84532002`: 12 requests per 60 seconds, one bucket per client address, for an enabled `/health`.
   - `POINTS_GLOBAL_LIMITER`, namespace `84532003`: 50 Durable Object wakes per 60 seconds for the whole location, on one shared key. These bindings count separately in each Cloudflare location. This cap is charged only when the request is about to call the object. An enabled `/health` charges it on a cache miss.
   `OPTIONS`, a disabled route, and an unknown path are not counted. A request with no `CF-Connecting-IP` is rejected with 400 `client_address_required` and is not placed in a shared bucket.
   A disabled `/health` or `/v1/points` route returns 503 before anything else, including when a query parameter is repeated. `/health` uses `{ "status": "disabled" }`. `/v1/points` uses `points_disabled`. Every `OPTIONS` returns 204, including a repeated query parameter, a disabled route, `/health`, and an unknown path. It does not use a limiter and does not wake the object.
   On an enabled route that has a client address, the order is the per-address limiter, then a repeated query parameter. That repeated parameter returns 400 `duplicate_query`, with the same CORS headers as a normal read. The 400 uses one per-address slot. It does not use the global cap, and it does not wake the object. An unknown path with a repeated parameter is also that 400 and does not use a limiter slot. The 429, the disabled 503, a missing client address, `/health`, and that unknown-path 400 all carry the CORS headers.
5. Set the RPC endpoint only with `npx wrangler secret put BASE_SEPOLIA_RPC_URL`, then paste the value at the prompt. Use your keyed endpoint or the public Base Sepolia JSON-RPC endpoint. A plain var is wiped by the next `wrangler deploy`. A secret is kept. Do not put the URL in `wrangler.toml`, `.dev.vars`, or the repo. The first alarms report `config_error` and reschedule until this secret exists.
6. Leave `POINTS_ENABLED` unset until the Verifier gives GO. Only the exact string `true` turns the indexer on. `TRUE`, `1`, `yes`, `on`, and a padded value stay off. While it is off, `/health` returns 503 `{ "status": "disabled" }` and does not wake the Durable Object. Every `OPTIONS` is answered in the front Worker with 204 and does not wake it either. `/v1/points/*` returns 503 `points_disabled`. When it is on, `/health` is limited per address, then stored in the Cache API for 15 seconds, so a poll does not wake the object on every call. That cache only stores the response on a custom domain. On `workers.dev` the Cache API does not store it, so each poll still counts against the global cap. A cache miss counts against the global cap and then reads the object, because that is where behind/ok is stored. `/v1/points/*` counts against the 20 per minute per-address limit and the global cap before the object is called.
   Every disclaimer link slot is published only as https. The slots are `master_disclaimer`, `legal_notice_url`, `as_is`, `not_investment`, `eligibility_notice`, and `abuse_policy`. The value must start with `https://`, have a host, and have no username or password. `http`, `data:`, a relative path, and `https:example.com` become null. An uppercase scheme is kept only after it is normalized to `https://`.
   After an error that is not `config_error`, the next alarm waits 1 second, then that wait doubles, and it stops growing at 15 minutes. A small jitter is added. `POINTS_FAST_PACE=1` skips the jitter. A pass that finishes clears the wait, and a pass that was already clear does not write the zero again. `config_error` stays on `POINTS_POLL_MS` (15 seconds unless you change that setting). `/health` then shows that poll wait in `error_backoff_ms`, and the next RPC failure starts again at 1 second.
7. Free plan budgets, for one location:
   - Durable Object requests: 100,000 per day, and alarms count. A caught-up alarm every 15 seconds is 86,400 / 15 = 5,760 requests a day. The global HTTP cap is 50 per minute, which is 72,000 a day. The sum is 77,760, leaving 22,240 for extra catch-up alarms on the 1 second cadence. A full day of 1 second alarms is about 86,400 by itself and does not fit beside a full HTTP cap, so a long catch-up has to stay short. The cap is per location. Several saturated locations can add past 100,000. This is the control available on the Free plan.
   - Rows written: 100,000 per day. QA measured about 63,000 rows a day at steady state, about 10 meta rows and one alarm schedule on each 15 second pass. Reads do not write a hit table. The front Worker limits in front of the object. A full day in the 1 second catch-up loop can pass 100,000 row writes. Watch the row counter if the cursor stays behind.
   - A caught-up alarm is every 15 seconds. A persistent RPC error does not stay on the 1 second cadence: `error_backoff_ms` doubles up to 15 minutes, so that failure stays far under a full day of 1 second alarms.
   - If stored logs pass 500, a rebuild stops, the rows already stored stay, `dirty` stays set, and `/health` reports `rebuild_capped`. That bounds CPU when someone emits a flood of cheap logs. This build has no prune. Do not delete the Durable Object to clear the flag. Leave scoring off. The console line is `{ "message": "rebuild_capped" }`.
   - If `/health` shows `removed_finalized`, a `removed: true` log arrived at or below that alarm's RPC finalized head. The stored raw log was kept. Read the `removed_finalized_log` console line for the block. Do not delete the row by hand. Treat it as a chain anomaly before scoring.
   - The `nonces` and `origins` tables are intentionally unwritten, so scores stay at 0 until screening fails closed.
8. Later, when the lookup UI exists, put the Worker URL in `apps/wallet-ux` and rebuild that app. Do that only after the Verifier GO.
9. Confirm the Render dashboard has no `points-indexer` service. `services/points-indexer/render.yaml` says nothing there is deployed. There is nothing to retire.

Must-fix before scoring goes live. Do not turn scoring on until both of these exist. They are not in this build:

1. A way to prune or compact logs past the 500-log rebuild cap.
2. A lying RPC can invent logs. Block hashes and receipts must be checked, or two RPCs must agree, before scoring goes live.

Workers Logs are on with `head_sampling_rate` 1, so our error and lag lines are kept. `observability.logs.invocation_logs` is false, so Cloudflare's per-request invocation log is not stored. Traces stay off (`enabled` false and sampling 0) on their own. `.dev.vars` and `.wrangler/` are gitignored.

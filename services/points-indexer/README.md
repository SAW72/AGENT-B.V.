# Points indexer

Internal dev notes for the off-chain Base Sepolia ledger. Chain id `84532` only. Chain ids `1` and `8453` are refused. There is no token, no balance that can be transferred, and no UI in this package.

The rules implemented here are the ones in `docs/AGENT-BV-POINTS-SPEC.md` and `docs/reputation/EVENT_MAP.md`. This package does not change contracts.

```bash
cd services/points-indexer
npm test
npm start
```

`src/main.mjs` is the process entry. Importing it does not open a poll loop. `loadConfig` reads environment variables only (`BASE_SEPOLIA_RPC_URL`, `CHAIN_ID`, `ESCROW_ADDRESS`, `POINTS_DB_PATH` or `DATABASE_URL`, `POINTS_POLL_MS`, `POINTS_LOG_RANGE`, `POINTS_MAX_WINDOWS_PER_PASS`, and the optional read-API flag `POINTS_ENABLED`). The other read-API settings (`POINTS_CORS_ORIGINS`, `POINTS_TRUSTED_PROXY_HOPS`, `POINTS_READ_RATE_PER_MINUTE`, `POINTS_BREAKER_FAILURES`, `POINTS_BREAKER_COOLDOWN_MS`) are read from that same env object when the read module is first loaded. Pace settings are read separately by `loadPaceSettings` and do not stop the process when a value is missing or invalid. `start({ rpc, once: true })` takes an injected client and returns. A chain id other than `84532`, an RPC that reports another chain id, an escrow or panel address with empty contract code, or a missing, zero, or malformed escrow address stops the process before logs are read. A failed log scan does not. The process keeps serving `GET /health` and retries on the poll timer.

Each pass reads finalized logs in windows of at most `POINTS_LOG_RANGE` blocks (default `200`, matching the public Sepolia `eth_getLogs` limit of `toBlock - fromBlock <= 200`). The first block is `max(47715415, last_scanned_block + 1)`. The cursor is `last_scanned_block` in the `meta` table and is written in the same SQLite transaction as that window's raw logs. A non-array `eth_getLogs` result leaves the cursor where it is (`unverifiable_log`). On the live client, each block header is read before the commit. A bloom that cannot contain the escrow or the panel accepts an empty result for that block. A bloom that might contain either address, or a bloom the client cannot read, requires receipts (`eth_getBlockReceipts`, or one receipt per transaction when that method is missing). The window commits only when those receipt logs for the watched addresses match the scan, including a verified empty block. A short log list, a missing receipt, or a mismatched block hash holds the window (`logs_incomplete` or `logs_unverified`) and the next pass retries the same cursor. An injected test client without `getBlock` does not run that check. A crash after the fetch and before commit leaves the cursor where it was, so the window is read again. A range error is JSON-RPC `-32614`, HTTP 413, or range text on `details` / `shortMessage` (not the full viem message). When that text says `limited to a N range`, the next window is `N` blocks inclusive, clamped to at least 1 and at most `POINTS_LOG_RANGE`. Otherwise the window is halved, down to one block. A failure at one block is raised, and the cursor is not moved past it. The shrunk window is remembered for later passes in the same process and doubles after each successful window until it is back at `POINTS_LOG_RANGE`. Setting `POINTS_LOG_RANGE` above the public RPC 200-block limit (`toBlock - fromBlock` over 200) makes that learned window oscillate: a success doubles it, the next getLogs fails, and the size clamps back, so about one request fails per successful window. A new process starts at the configured value.

`eth_getLogs` runs at most five times a second. The gap between the start of one call and the start of the next is at least 200 ms, including a retry of the same window. Chain id, both contract-code reads, and the finalized-head read use that same gap and the same retry limit. The finalized head is `eth_getBlockByNumber` with the tag `finalized`. The cursor moves only through blocks that pass actually scanned. When the reported finalized head is below the stored head, the pass scans nothing, logs `head_behind`, and leaves the cursor where it is. The gap clock is monotonic (`performance.now`, or `paceNow` in a test). `Date.now` is used only to turn an HTTP-date `Retry-After` into a delay and to carry a wait that was longer than the cap. The clock and the sleep live in `src/pace.mjs` and are passed in by tests. That module does not open sqlite and does not assume the database file is still on disk for the next pass.

Every JSON-RPC request sends `User-Agent: Agent-B.V. points-indexer` unless `POINTS_USER_AGENT` is a safe override: 1 to 128 characters from letters, digits, space, and `. , _ + : ( ) / -`. A blank value or anything else, including a carriage return or line feed, keeps the default. The HTTP timeout is `POINTS_HTTP_TIMEOUT_MS` (default `10000`).

HTTP 429 reads `Retry-After` when the header is present. The value is an integer number of seconds or an HTTP-date in IMF-fixdate, RFC 850, or asctime form. A fraction, a leading minus, or any other text is ignored, and the pass uses the 1 s, then 2 s, then 4 s schedule. A past HTTP-date waits 0 ms from this rule, and the 200 ms gap still applies. A wait of 30 seconds or less stays inside the pass. A longer `Retry-After` sleeps 30 seconds, ends the pass without using the remaining retries, and the next pass waits the remainder before any RPC, including the head read. The carried wait is at most 15 minutes from that response. A longer header is capped and the log line is `retry_after_capped`. The deadline is stored as `rpc_not_before` in the sqlite meta table. A fresh deploy with no database file creates that file so the deadline is kept, and a restart waits it out before chain id, contract code, or the head read. The sleep itself is at most 15 minutes, including when the clock steps backward. `stop()` cancels a carried sleep that is still pending. asctime dates are read as GMT. A `Retry-After` over 30 seconds on chain id or contract code ends that attempt and leaves the process running for the next pass. HTTP 5xx and network errors use those same three waits. A `Retry-After` header on a 5xx response follows the same rule. After 3 retries the pass returns at the last window whose raw logs and `last_scanned_block` committed together. It does not throw. The same three retries apply to chain id, contract code, and the finalized head. If the head read is still failing, the pass returns `rate_limited`, `server_error`, `network_error`, or `head_lag` and does not open the ledger when that happens before the first open. Chain id and contract code still stop the process when every retry fails. The poll timer starts the next pass on its normal interval. `GET /health` keeps the same keys. Until a later pass finishes, `error` is `rate_limited`, `server_error`, `network_error`, or `head_lag`. A fresh 200 includes that key. When nothing has committed and the freshness window has not started, the status stays 503 and `error` is the same code. The viem HTTP transport is created with `retryCount: 0`, so those waits are the only retry layer.

A 429 is not a block-range error, including when the text contains `exceed`. Rate-limit text on `details` or `shortMessage` (`rate limit`, `rate exceeded`, `too many requests`, `request limit`, `quota`, `throttle`, `compute units`, `capacity`, `credits exceeded`, `daily request count exceeded`, `limit exceeded`) is not a range error either, including JSON-RPC `-32005` with that text. `query exceeded the cap`, `block range exceeded`, `block range limit exceeded`, and `-32005` `too many results` stay range errors. A bare `limit exceeded` is still a rate limit. A JSON-RPC `-32602` whose text says the range extends beyond the current head is `head_lag`: the same window is waited and retried, and it is not shrunk. HTTP 413, JSON-RPC `-32614`, and the other range messages still shrink the window, or fail when the window is one block. `-32602` text such as `block range is too large` is still a range error.

A pass commits at most `POINTS_MAX_WINDOWS_PER_PASS` windows (default `500`). Those cursors are already stored, and the next pass continues at `cursor + 1`. `POINTS_MAX_WINDOWS_PER_RUN` is optional. Unset, blank, or invalid means no extra cap, which is the current behaviour. A positive integer (for example `40`) caps that one pass. It does not stop the process. When the cap stops the pass while blocks remain, `GET /health` reports `error` `run_cap` and `behind`. The next pass continues from the cursor. The finalized head never moves backward. Progress time uses a monotonic clock. The pass calls `rebuild()` once when a window inserted raw logs, when the finalized head is about to move over a stored log that is still above the previous head, or when a previous rebuild failed after its commit. That crossing is decided before the new head is stored. An empty window does not rebuild. A failed rebuild leaves `GET /health` not ok with `error` `rebuild_error` until a later rebuild finishes. A window commit on its own does not clear that. A commit crash after an earlier window has inserted leaves the ledger stale together with the dirty flag, so `/health` stays not ok until the next rebuild. A tick that starts while a pass is still running is skipped.

Pace environment variables, with the defaults this process keeps when the variable is unset or invalid:

| Variable | Default |
| --- | --- |
| `POINTS_GETLOGS_MIN_GAP_MS` | `200` |
| `POINTS_RETRY_BACKOFF_MS` | `1000,2000,4000` |
| `POINTS_MAX_SCAN_RETRIES` | `3` |
| `POINTS_MAX_RETRY_AFTER_MS` | `30000` |
| `POINTS_GETLOGS_GAP_JITTER_MS` | `0` |
| `POINTS_RETRY_BACKOFF_JITTER_MS` | `0` |
| `POINTS_HTTP_TIMEOUT_MS` | `10000` |
| `POINTS_HEALTH_FRESHNESS_POLLS` | `3` |
| `POINTS_MAX_WINDOWS_PER_RUN` | unset |
| `POINTS_USER_AGENT` | `Agent-B.V. points-indexer` |

Jitter is added on top of the gap and on top of a schedule slot. It is not added to a readable `Retry-After`. A backoff wait, including that jitter, is at most 15 minutes and stays under the timer limit. A default of `0` leaves the gap at 200 ms and the waits at 1 s, 2 s, and 4 s. `POINTS_RETRY_BACKOFF_MS` is a comma-separated list of positive integers. A bad list falls back to `1000,2000,4000`. `POINTS_GETLOGS_MIN_GAP_MS` must be an integer from 100 to 60000, `POINTS_MAX_RETRY_AFTER_MS` from 1 to 30000, `POINTS_HTTP_TIMEOUT_MS` from 1 to 120000, and `POINTS_MAX_SCAN_RETRIES` from 1 to 8. `0` and anything above those ceilings fall back to the defaults in the table. Each backoff slot must be an integer from 1 to 30000, and the list is at most 8 slots.

`POINTS_DB_PATH` is the sqlite file. Set it to a persistent path when the host has durable storage. `DATABASE_URL` is still the fallback when `POINTS_DB_PATH` is unset. A `DATABASE_URL` value is opened as a sqlite file path, so a Postgres URL or any other non-file URL is not a connection string. The reference `render.yaml` keeps the file under `/tmp` and does not add a disk.

`GET /health` is `200` when the last committed window, or a successful pass, is still within `POINTS_HEALTH_FRESHNESS_POLLS` poll intervals (default three). While the cursor is behind the finalized head that response includes `behind` (the block gap). It is `503` when that progress is older than that window. A `503` body carries a short `error` code such as `rpc_error`, `range_error`, `ledger_error`, `config_error`, or `finalized_unsupported`, and not the provider message. `finalized_unsupported` means the provider rejected the finalized block tag. A fresh 200 can also carry `error` `run_cap` or `head_behind` while the cursor is still behind. While a rebuild is due and has not finished, `/health` is not ok and `error` is `rebuild_error`. While the ledger is still stale, a later head failure or a crash keeps that label. A finished rebuild clears it, and a pass that then ends on a 429 reports `rate_limited`. A crossing query that throws leaves the rebuild due even when no stored log was crossed, and the next pass rebuilds once. Log lines are redacted the same way: the configured RPC URL, any `http(s)` or `ws(s)` URL (including one split by spaces), a percent-encoded scheme, a query secret such as `?auth=`, a bare key, a 32-character hex key, a short key-like path segment, and a key used as a hostname label are removed before the line is written. `shortMessage` is cut to 512 characters before that redaction. `/health` does not change when the read API below is mounted.

## Read API

This is the Agent-B.V. read-only preview for Base Sepolia. `src/readApi.mjs` exports `createReadApi({ store, config, now, enabled, log })`. The module can be imported on its own. It does not open a database, and it does not read `process.env`. The host passes an env object into `pointsEnabled` and `readSettings`. The names that object may carry are `POINTS_ENABLED`, `POINTS_CORS_ORIGINS`, `POINTS_TRUSTED_PROXY_HOPS`, `POINTS_CLOUDFLARE_INGRESS`, `POINTS_READ_RATE_PER_MINUTE`, `POINTS_BREAKER_FAILURES`, and `POINTS_BREAKER_COOLDOWN_MS`. The module does not read a relayer key, a private key, or a signing key, and it does not import the claim relayer. `pointsEnabled` lives in `src/pointsFlag.mjs`. The process entry uses that same function, so the flag is parsed once.

The core calls four methods on the injected store: `getCursor()`, `getLedgerSummary(address)`, `listLedgerRows(address, { limit, after })`, and `getConfig()`. `after` is null or `{ block_number, log_index, action, utc_day }`. It does not call a database driver. `handle({ method, path, query, headers, remoteAddress, origin })` returns `{ status, headers, body }`. `createReadApi` mounts that function on a node request listener. `src/readApiSqliteStore.mjs` is the sqlite adapter. On a file database the process opens a second connection with `readOnly: true` (`src/readConnection.mjs`) and passes that handle in. The writer keeps its own handle. An in-memory database has no file to share, so that test path still uses the writer handle. A restart that drops the file does not have to leave a path behind.

`main.mjs` loads the core and the sqlite adapter with `import()` only when `POINTS_ENABLED` is on for the request. While the flag is off, the process does not load either module. `POINTS_ENABLED` gates the public read routes only. `GET /health` stays available for a host health check. The indexer loop does not read this flag.

`POINTS_ENABLED` is checked on every request. It is on only when the value is the exact string `true`. `TRUE`, ` true `, `1`, `yes`, `on`, blank, and an unset value are off (this is the default). While the flag is off, `GET`, `HEAD`, `POST`, and `OPTIONS` under `/v1/points` return `503` with `{ "ok": false, "error": "points_disabled" }`. The process sends that answer before the module loads, so the response has no CORS headers. `/health` is unchanged.

Chain id `84532` only. A missing or blank `chainId` query defaults to `84532`. Any other value, including `1`, `8453`, and non-numeric text, is `400` `wrong_chain`. An address must be `0x` plus 40 hex digits. The stored and returned address is lowercase. Anything else on an address route is `400` `invalid_address`.

| Status | When | Body | Extra |
| --- | --- | --- | --- |
| 200 | A known `GET` or `HEAD` | The object for that route. `HEAD` sends the same headers and an empty body | |
| 204 | `OPTIONS` on a known route | Empty | `Allow: GET, HEAD, OPTIONS` |
| 400 | Chain, address, limit, cursor, or a repeated query parameter is rejected | `{ "ok": false, "error": "wrong_chain" }`, `invalid_address`, `invalid_limit`, `invalid_cursor`, or `duplicate_query` | |
| 404 | Unknown path under `/v1/points` | `{ "ok": false, "error": "not_found" }` | |
| 405 | Known route, method other than `GET`, `HEAD`, or `OPTIONS` | `{ "ok": false, "error": "method_not_allowed" }` | `Allow: GET, HEAD, OPTIONS` |
| 429 | Rate limit exceeded | `{ "ok": false, "error": "rate_limited" }` | `Retry-After` seconds |
| 500 | The store throws | `{ "ok": false, "error": "internal" }` | No stack, message, URL, or path. One log line: `points_read internal` |
| 503 | Flag is off | `{ "ok": false, "error": "points_disabled" }` | |
| 503 | The breaker is open | `{ "ok": false, "error": "points_unavailable" }` | |

Every response from this module, and the `points_disabled` response sent before the module loads, includes `X-Content-Type-Options: nosniff`. A thrown read and the moment the breaker opens are logged as `points_read internal` and `points_read breaker_open`. The log line is that code only. It does not include the thrown message, a stack, a URL, or a path.

After `POINTS_BREAKER_FAILURES` consecutive thrown reads (default 5), later requests that would call the store get `503` `points_unavailable` until `POINTS_BREAKER_COOLDOWN_MS` milliseconds have passed (default 30000). The clock is the injected `now`, or `Date.now` when the host does not pass one. When the cool-down has elapsed, one store read is allowed through. A completed store read closes the breaker. A thrown read opens it again and the cool-down starts over. The thrown read itself is still `500` `internal`. `points_disabled` and `points_unavailable` are not counted as failures. A `400`, `404`, `405`, or `429` that never called the store does not close the breaker and does not clear the failure streak. The handler does not throw out of the request callback. While the breaker is open, that short response does not call the store and does not use a rate-limit slot.

Paths outside `/v1/points` keep the previous plain-text `404`. Every read-API response from the module sends `Content-Type: application/json; charset=utf-8` (except `204`) and `Cache-Control: no-store`. The `points_disabled` response sent before the module loads uses that same JSON content type and `Cache-Control: no-store`, without CORS headers. CORS is an exact-origin allowlist from `POINTS_CORS_ORIGINS` (comma-separated `https` origins, set at deploy time). When that variable is unset or empty, the allowlist is empty and no `Access-Control-Allow-Origin` header is sent, including on `OPTIONS`. `Vary: Origin` is still sent. There is no `*` origin and no built-in origin. A disallowed or missing `Origin` gets no `Access-Control-Allow-Origin` header. `OPTIONS` is the preflight.

The in-memory limiter allows `POINTS_READ_RATE_PER_MINUTE` requests per client in a 60 second window. **60 per minute is a DESIGN DEFAULT, not a measured or security value.** A blank or malformed setting falls back to that default. The window is empty again after the process restarts. `OPTIONS` is not counted.

`clientIp` uses the socket address unless `POINTS_TRUSTED_PROXY_HOPS` is set to a positive integer. The default is `0`: `X-Forwarded-For` is ignored. This package does not choose a host. A check of Render's published header behavior, done without a deploy, did not show that the rightmost entry is the client. Render's article "How Render handles DDoS attacks" (https://render.com/articles/how-render-handles-ddos-attacks, 2026-04-01) says traffic passes through Cloudflare and then Render's load balancer, and its example reads the leftmost address (`split(',')[0]`). Render's founder wrote on 2021-05-28 that the first IP in the list is the real client (https://feedback.render.com/features/p/send-the-correct-x-forwarded-for). A measured report of the same header shows `<client>, <cloudflare edge>` with the socket on a private proxy address, and says the header is appended rather than replaced (https://rohitpaulk.com/articles/render-rails-remote-ip.html). Those sources disagree on which entry is safe, so the hop count stays `0` until an operator sets it for a proxy they have checked. A set count still reads that many positions from the **right**, never the leftmost on its own. A missing, empty, over-long (more than 2048 characters), malformed, or too-short header falls back to the socket address. IPv6 clients share a `/64` bucket. IPv4-mapped IPv6 is treated as that IPv4 address. The map has a max-entries cap (default 4096). Expired keys are dropped first. When the map is still full, a new key is refused with `429` and a key that is still inside its window is left in place. A sweep timer also drops expired keys. Setting `POINTS_TRUSTED_PROXY_HOPS` above `0` with no proxy in front lets a client choose its own `X-Forwarded-For` key. `CF-Connecting-IP` is read only when `POINTS_CLOUDFLARE_INGRESS` is the exact string `true`, which means the process is reached only through Cloudflare. The default ignores that header and keeps the socket address. The timer is `unref`'d so it does not keep the process alive. The on/off flag is checked on every request, before the module is loaded. The allowlist, hop count, rate, and breaker thresholds are read when the module is first loaded.

`GET /v1/points/config` returns `chainId` `84532`, `status` `"draft"`, the `weights` and `gates` objects from `config/points.json` (every value is null today), `rule_version`, and `disclaimer`. That file has no rule-version field, so `rule_version` is null. `disclaimer.text` is the shared sentence used by the address and history routes. `disclaimer.links.legal_notice_url` is null until a notice URL is set.

`GET /v1/points/:address` is one entered address. `points_total` is `0` on this preview. Checklist #7 is open, so the response sets `points_withheld` to true and does not show a sum of withheld points. The sqlite summary adds `points` only where `points_withheld` is `0`. The preview still returns `points_total` `0` for the address route. `points_withheld` is true and `eligibility` is `{ "status": "unverified", "reason": "ofac_unconfigured" }`. `rows_count` is the number of committed rows for that address on chain `84532`, including withheld rows. `first_activity_utc_day` is the `utc_day` of the `first_activity` row, or null. `indexed_to_block` is `last_scanned_block` (null when that cursor has not been written). It is not `finalized_block`. `behind` is the gap from that cursor to the finalized head the host reports for the pass. That head is the greater of the stored finalized block and the live head read at the start of the current pass, so a restart that is still scanning does not report a zero gap. The stored block is written when the pass finishes. When there is no cursor and the head is at least block `47715415`, the gap is measured from that block. `syncing` is true when `behind` is greater than 0, when the gap is unknown, or when no pass has succeeded yet. `stale` is true when the last pass failed, including an RPC outage, or when a rebuild is still due. A window commit on its own does not clear it. The body does not include the provider message. A client can show a zero total as still in progress while `syncing` or `stale` is true. The `disclaimer` object uses one shared sentence, `Testnet only. Not a token. Can't be transferred, sold, or redeemed. May be adjusted or cancelled, and does not convert to anything.` The link slots are null, including `legal_notice_url`.

Address fields: `address`, `chainId`, `points_total`, `points_withheld`, `eligibility` (`status`, `reason`), `rows_count`, `first_activity_utc_day`, `indexed_to_block`, `finalized_block`, `behind`, `syncing`, `stale`, `disclaimer` (`text`, `links`). Config fields: `chainId`, `status`, `weights`, `gates`, `rule_version`. `docs/AGENT-BV-POINTS-SPEC.md` is not edited here.

`GET /v1/points/:address/history` pages committed `ledger_rows` only. The page order is `block_number`, `log_index`, action rank (`fund`, `release_or_refund`, `dispute_open_or_vote`, `first_activity`, `return_day`), then `utc_day`. The cursor is an opaque keyset of those fields, not `seq`. Rebuild deletes `ledger_rows` and assigns `seq` again, so a `seq` cursor would move. A missing `limit` is 25. A canonical integer above 100 is clamped to 100 and still returns `200`. `0`, a negative number, and non-canonical text (`abc`, `1.5`, `01`) are `400` `invalid_limit`. A bad `cursor`, including a bare integer, is `400` `invalid_cursor`. These page sizes are the behavior of this preview. They match `read_api.history_page_default` and `read_api.history_page_max` in `config/reputation/sepolia.json`. Each item is a new object with only `action`, `utc_day`, `tx_hash`, `log_index`, `block_number`, `escrow_id`, `points`, `points_withheld` (boolean), `eligibility_reason`, and `register_status`. `points` is `0` when `points_withheld` is true. The handler does not return the sqlite row. History also includes `limit`, `next_cursor`, and the same `indexed_to_block`, `finalized_block`, `behind`, `syncing`, and `stale` fields. Error codes for these routes are `wrong_chain`, `invalid_address`, `invalid_limit`, `invalid_cursor`, `not_found`, `method_not_allowed`, `rate_limited`, `internal`, `points_disabled`, and `points_unavailable`.

`Dockerfile` and `render.yaml` in this directory are reference config for a Node 22 web process with `GET /health`. They are not a repo-root Blueprint. This package does not create or deploy a service. `BASE_SEPOLIA_RPC_URL` is `sync: false` and has no value in git.

Tests use `fixtures/base-sepolia-logs.json`, a read-only `eth_getLogs` capture. They do not dial a network and they sign only with keys generated inside the test process.

## What it stores

SQLite ledger. A chain-log row is inserted only when all of the following hold:

- The log is not `removed`, and its block number is at or below the finalized head. `safe` is not a commit path. There is no cancel or rewrite of a committed row.
- The wallet comes from the event (`payer`, `payee`, `party`, or `voter`). `transactionFrom` is stored and never credited.
- `VoteCast` counts only when its `disputeId` matches a 3-argument `EscrowDisputed` from escrow `0x3d660502d75f1e97b08c110255921b437a3c4c42` at or after block `47715415`. The panel address is not admitted by its own deploy block.
- `Credited`, `DisputeResolved`, `DisputeOpened`, and the retired 2-argument dispute topic are ignored.
- A server-issued nonce is bound to `(txHash, logIndex, wallet)`. It can be revoked and, after it is consumed, reissued inside the stored issue window. The window is `issue_time <= block_timestamp + 86400` of the bound log. Rebuilds read the stored issue time and the stored revoke. They do not ask the wall clock again.
- `PointsLink` is EIP-712, domain name `Agent-BV Points`, version `1`, chain id `84532`, verifying contract the escrow above. The signature is 65 bytes, low `s`, `r` and `s` non-zero, `r` below the curve order, `v` in `{0, 1, 27, 28}` with `0 → 27` and `1 → 28` before recovery. Anything else, including an ERC-1271 blob, is refused.
- The decision-chain terminal entry is a human with a server-side identity anchor and behavioral signals, and its timestamp is strictly before the log's block timestamp. `accountable_human_id` does not pass that check. An `ai` terminal entry stores the chain and commits no row.
- Checklist #7 is open. Every committed row has `points = 0` and `points_withheld = 1`, and it still occupies the unique keys. Before a row is stored, the indexer checks the wallet against a local cache of OFAC digital-currency addresses. The cache refreshes every 24 hours from the public SDN advanced list. The refresh streams that publication and keeps the issue date plus digital-currency features only. It does not buffer the XML. A Workers isolate has 128 MB of memory, and the file is allowed to be up to 160 MB on the wire. The retained extract is capped at 8 MB, and that ceiling does not grow with comments or chunk size: only a short issue date, feature-type labels, and the addresses themselves are kept. A feature whose type has not been declared, a truncated file, an oversized read, an element over 256 KB, more than 1024 feature types, an empty or undersized address list, a fetch that exceeds 60 seconds, a redirect other than one HTTPS hop from `sanctionslistservice.ofac.treas.gov` to the public publication bucket under `/Published/`, or an HTTP failure does not replace a cached list. A cached list older than 48 hours, or a cached list with fewer addresses than the minimum (default 100), is unavailable. A refresh that would shrink a good list to less than half also fails closed and keeps the cached list. A match is stored as `eligibility_status = ineligible` and `eligibility_reason = sanctions_match`. That match is kept in `sanctions_wallets`, which a rebuild does not delete, so a later scan stays ineligible even if the refreshed list no longer has the address. Any other wallet stays `unverified` / `ofac_unconfigured`, including when the list is missing and when the wallet is not on the list. A clear check is not an eligibility approval. Each wallet check is appended to `sanctions_checks`. The worker alarm is the only path that fetches the list, and that alarm does not run while `POINTS_ENABLED` is unset.
- A repeated `escrowId` on `EscrowCreated`, or a repeated `disputeId` on `EscrowDisputed`, is ambiguous. Both copies and every release, refund, or vote that joins that id are skipped. Nothing is credited.
- `PointsLink.nonce` and `PointsLink.logIndex` must be canonical decimal strings (`/^(0|[1-9][0-9]*)$/`) before they are turned into `BigInt`. Hex, a leading minus, an empty string, whitespace, and non-numeric text return `bad_link` and do not throw.
- Live payer, payee, and voter accounts can be EIP-7702 delegated EOAs (`0xef0100` plus a delegate address). This indexer does not read account code. A 65-byte ECDSA signature that recovers to the EOA key is accepted. Contract-code signatures, including ERC-1271 blobs that are not 65 bytes, stay refused.

`config/arbitrator-register.json` is the off-chain human/AI register. It ships empty. A matched vote stays `pending` with points 0 until that voter is registered. An `ai` registration stores the row and does not count it toward `return_day`. A `human` registration still stores points 0 while the vote weight is unset. A configured vote weight above 0 is what makes a human vote count toward `return_day`. That check is separate from the #7 zero.

Numeric weights and the farming gates (`same_pair_per_day`, `same_pair_lifetime`, `min_escrow_amount_wei`, `min_escrow_duration_seconds`) stay null until set. A null gate is not applied.

## Keys

```text
UNIQUE (wallet, action, utc_day)
UNIQUE (chain_id, contract, tx_hash, log_index)
  WHERE action IN ('fund', 'release_or_refund', 'dispute_open_or_vote')
UNIQUE (wallet) WHERE action = 'first_activity'
UNIQUE (wallet, utc_day) WHERE action = 'return_day'
```

`log_index` and `block_number` are `NOT NULL` on every row, including derived rows. `wallet`, `contract`, and `tx_hash` are lowercase `0x` hex. `utc_day = floor(block_timestamp / 86400)`. `00:00:00Z` is the new day. Ingest time is not the day.

`first_activity` is the derived one-per-wallet row. The spec renamed the earlier name. Its chain-log columns are copies of the source row, and `source_action` names that row. `return_day` uses the same copy rule. Neither derived action is inside the chain-log unique index, so the copy does not collide with the source.

A full rebuild deletes `ledger_rows` and replays raw logs, chains, nonce records, links, origins, the register, and the gates. It does not delete `sanctions_wallets` or `sanctions_checks`. Replay of the same log does not insert a second raw row or a second credit.

## QA notes

- M-1. Finalized-only. A log above the finalized head is withheld. A `removed` log is skipped. There is no safe-row cancel path, because a safe log is never committed.
- M-2. The derived-row indexes are the ones in the spec, under the name `first_activity`. A partial index of `action <> first_activity` would also cover `return_day` and would reject the return-day copy of the source key. The spec's `IN (...)` list is the one created here.
- M-3. The EIP-712 domain, the struct, and the nonce binding are implemented as above, including revoke and reissue. Tests sign with process-generated keys only.
- M-4. `docs/reputation/EVENT_MAP.md` already says release is payer-only while Open and payer or payee while Disputed, and that refund is the permissionless path. This package follows that wording. It does not edit that file.
- L-1. The chain belongs to the credited wallet. A refund whose `transactionFrom` is the claim relayer still requires the payer's chain.
- L-2. `wallet`, `contract`, and `tx_hash` are lowercased before the key is written.
- L-3. UTC day is `floor(block_timestamp / 86400)`. A second `release_or_refund` for the same wallet on that day is not deferred.
- L-4. Walk order is `(block_number, log_index)`, including when the raw logs arrive shuffled. A zero-point escrow row still counts as a `first_activity` source. A log that was not stored does not.
- L-5. The derived action is `first_activity`.
- L-7. A `VoteCast` whose `disputeId` matches only a retired escrow is not counted.
- N-1 through N-9. Expiry and the issue window are compared to the bound log's block timestamp. Confirmation time is not. Rebuilds read stored nonce records. A vote with unset weight does not produce `return_day`. An escrow row at points 0 does.
- P-2. `dispute_open_or_vote` stays one action. Splitting it is still open in the spec.
- Checklist #9, the O1–O5 reputation ledger, and any dashboard are out of scope. Flags do not write a negative point. No contract, key, or deploy is part of this package.

## Ambiguities resolved

- The idempotency key `(chain_id, contract, tx_hash, log_index)` applies to chain-log actions. Derived rows copy those columns and are excluded by the partial index, with their own unique keys, and they point at the source through `source_action` plus the copied key.
- `return_day` for a vote follows the configured vote weight and a `human` register entry, not the stored points column. Stored points stay 0 while checklist #7 is open, including when the weight is set. `VoteCast` does not start `first_activity`, so that later day still requires an earlier stored escrow-log row for the same wallet.
- A nonce is consumed only when a chain-log row is inserted or when it is revoked. A cap or gate miss leaves the nonce open. A second open issue for the same key is refused by a partial unique index. After a confirmed row exists, a later nonce can be issued and its link does not add a second row. Rebuild writes the final nonce status and does not reopen a confirmed nonce in the database while another nonce for that key is open. If a replay would leave two open nonces, the latest issue stays open and the earlier one is revoked.
- The latest stored chain for `(wallet, action, escrow id)` is the one rebuild evaluates. A blocked chain is still stored.
